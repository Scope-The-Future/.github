# WEEEK

**При создании задачи:**

1\. Заполнить описание полностью, чтобы автору задачи как можно реже приходилось отвечать на уточняющие вопросы

2\. Поставить теги: тип задачи (зелёные теги) и сферу (синие теги), можно несколько

3\. Приоритет «Высокий» — только если стопорится вся разработка, в остальных случаях можно не указывать

4\. Выбрать соответствующую доску (обычно она совпадает с синим тегом)

5\. Прикрепить необходимые материалы, указать связанные задачи, если они есть

6\. Все ответы на вопросы и решения по задаче фиксировать в комментариях к ней, чтобы они не терялись

7\. Если вы сделали фичу по своей инициативе — создать задачу ДО создания ветки (номер нужен для названия ветки) и сразу перевести её в «Выполнение», чтобы на ревью было понятно, что вы сделали

**При взятии задачи:**

1\. Не затягивать: небольшие задачи, висящие в работе неделями, — плохо

2\. По мере работы переводить задачу по доске: «Выполнение» → «Ревью» → «Готово». В «Готово» её переводит только проверяющий после ревью

3\. При любых стопорящих вопросах писать комментарий в задаче; если ответа нет (в течение дня) — писать лично в Telegram

После выполнения задачи вы хвалите себя и берёте следующую :)

# GITHUB

1\. Для каждой задачи — своя ветка. Пушить в main нельзя: это запрещено защитой ветки на GitHub

2\. Название ветки: `<номер задачи в Weeek>-<краткое описание>` (+ латиницей, через дефис). Пример: `12-weeek-github-code-rules`

3\. После merge ветка удаляется автоматически

4\. В тексте коммита кратко описывайте, что сделано в коде

5\. Если задачу вернули на доработку, автор вносит правки в той же ветке (новыми коммитами в тот же PR)

6\. Откат смерженного PR делается через git revert

7\. Изменения не должны ломать работающее приложение: недоделанные фичи не влияют на существующую функциональность, а изменения API и данных остаются обратно совместимыми. Ответственность за это на авторе кода

8\. Секреты в git не попадают никогда (если попали — сразу сообщить команде, секрет нужно перевыпустить)

9?\. Для слияния PR нужен апрув от меня или человека, который не занимался этой задачей

Дополнительные правила по PR появятся после создания репозитория и первых PR

# CODE

1\. Названия переменных, функций, классов осмысленные и соответствуют нормам языка (для Python: snake_case для функций и переменных, PascalCase для классов, UPPER_SNAKE для констант)

2\. Сложные части кода комментировать; аннотации типов и описания в API обязательны

3\. JSON-файлы создавать по единому шаблону наименования для совместимости (шаблон будет определён позже)

4\. Особенности каждого языка будут описаны позже

Вы должны понимать, что делает каждый участок, и отвечаете за всё, что отправили на ревью. Любая ошибка — ответственность автора, но писать код можно любым способом.

Не отправляйте в ИИ-сервисы секреты, ключи и персональные данные.
